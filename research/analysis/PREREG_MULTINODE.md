# Pre-registration: does the load actually spread across nodes? (W7)

Frozen and pushed before the campaign runs. The push event is the timestamp
anchor (cardinal rule R1).

## Question (and provenance)

`FINAL_ROADMAP` §0 lists W7 — *"Single machine, single cluster"* — among the
weaknesses a Transactions reviewer will raise, and recorded it as unclosable
without the GPU-blocked B1 matrix:

> Demonstrating multi-node *behaviour* needs a high-demand cell, i.e. the
> GPU-blocked B1 matrix. Partial credit is not available here and should not
> be claimed.

Session 43 checked that and found it wrong on both halves.

1. **The CRUD path needs no GPU.** The 24 h soak (`RESULTS_LIVE_SOAK_V8.md`)
   drove 298.6 rps across sixteen pods with no model in the loop. High demand
   was never what stood in the way.
2. **Node placement was never measured.** `LoadDistributionSampler` reads
   `kubectl top pods`, which carries a pod name and a CPU figure and nothing
   else. No live record in this repository says which *node* served anything,
   so no sitting — at any demand, on any number of nodes — could have produced
   node-level evidence. The sampler now resolves each pod's node and writes
   `node_of` / `node_shares` into `load_distribution.json`.

This campaign is the first use of that measurement.

## What this is NOT

- **Not multi-host, and not multi-zone.** Every node here is a container on
  one machine sharing one kernel, one disk and one NIC. This cannot speak to
  network partitions, zone failure, or cross-host latency, and a PASS must
  not be quoted as if it did. W7's residue after this campaign is "single
  *machine*", not "single node".
- **Not a performance claim.** Nothing here compares controllers or measures
  cost. The question is whether work lands on more than one node at all.
- **Not a replacement for B1.** B1 remains blocked on GPU concurrency and
  scores different hypotheses (WL-H1/H2/H3) on the AI path.

## Design (frozen)

| | |
|---|---|
| experiment | `eval/experiments/multinode_crud.yaml` |
| backend | `cluster` (kind, created by the harness) |
| cluster size | **`medium`** — `NODES_BY_SIZE["medium"] = 4` nodes |
| workload | **`crud_bursty`** — CRUD only, so no GPU and no tier backend |
| systems | `jcac` |
| tenant mix | `uniform` |
| steps | 120 (10 s control interval → 20 minutes) |
| reps | 1 |
| evidence | `load_distribution.json` (`node_of`, `node_shares`, per-pod `shares`) |

`jcac` alone: the question is about placement, not about which controller
places better, and a second arm would double the sitting for nothing this
prereg asks.

## Hypotheses (frozen)

**MN-H1 (the claim).** Work reaches more than one node: **at least 2 distinct
nodes appear in `node_shares`, and the busiest node's share is < 0.90.**

The 0.90 is deliberate and stated before any number exists. A perfectly even
4-node spread is 0.25 each; the scheduler is free to pack, and packing is not
the failure this asks about. The failure is *pinning* — attempt 4's port-forward
put effectively 100% on one pod, and that is the shape MN-H1 must be able to
catch. A busiest-node share at or above 0.90 is pinning by any reading.

**MN-H2 (gating, and it can fail).** The measurement is sound: **`node_of`
resolves a node for every pod that appears in `cpu_ms`** — i.e. `node_shares`
contains no `"unknown"` bucket — and the sampler took **≥ 10 samples**.

If MN-H2 fails, MN-H1 is **VOID rather than FAILED**: an unattributed pod
means the instrument did not work, and a claim about node spread built on a
partial attribution is exactly the vacuous-instrument failure this project has
already hit three times in WP14.

**MN-H3 (descriptive, no verdict).** Report the per-node shares and the pod
count. If the deployment ran at one replica the whole time, MN-H1 is
**VACUOUS** — one pod can only be on one node, and that is a statement about
the demand, not about the cluster. Recorded as such, not as a PASS.

## Outcome handling and stopping rule

- **One sitting.** If the cluster fails to come up or the harness marks the run
  invalid, the sitting is VOID, disclosed, and re-run at most **once**. Two
  voids close the campaign as unresolved.
- Verdicts are written to `RESULTS_MULTINODE.md` as measured. A FAIL is
  published with the same prominence as a PASS: "the load pinned to one node
  on a four-node cluster" would be a finding about the deployment, and a more
  interesting one than the PASS.
- The record is generated by `analysis_multinode.py` from the committed
  evidence, never written by hand, and registered in `scripts/reproduce.py`.

## What a PASS does and does not license

A PASS licenses exactly: *"the control plane's work was observed on more than
one node of a four-node cluster under CRUD load."* It removes "single node"
from W7's residue and leaves "single machine" standing, which is the honest
remainder and is already listed in §8 as permanent.

It does **not** license "distributed", "multi-host", "fault-tolerant", or any
statement about behaviour under node loss. Nothing here kills a node.

## Sitting 1: VOID (2026-09-05, apparatus) — and Amendment 1

The first sitting ran 373 s and ended `valid_runs: 0`. Cause, from the run's
own recorded error:

```
POST /v1/tenants/t00/api-keys -> 404: {"error":{"code":"tenant_not_found", ...}}
```

The deployment came up as **19 pods across three workers**, and each control
plane held **its own SQLite**. Provisioning created tenant `t00` against one
pod and asked the next request for an API key, which landed on a different pod
that had never heard of it. Nothing to do with nodes, the workload, or the
sampler.

**The mistake was in this pre-registration, and it is mine.** The design above
said the AI env gates `trace_live.yaml` requires "do not apply here", which is
true of `POLYFORGE_EVAL_LIVE_AI` and the tier backends and false of
`POLYFORGE_EVAL_SHARED_PG=1`. That one is not an AI gate at all — it is the
session-23 fix for per-pod SQLite, and `live_soak.yaml`, the CRUD-only 24 h
soak with `LIVE_AI` unset, requires it for exactly this reason: "so every
control-plane replica writes one Postgres".

**Amendment 1, before the re-run.** The design gains one line:

| | |
|---|---|
| required env | `POLYFORGE_EVAL_SHARED_PG=1` — multi-replica storage, not an AI gate |

Nothing else changes. MN-H1's threshold, MN-H2's gate and MN-H3's vacuity
branch are all untouched, and no number from sitting 1 exists to have informed
them: the sitting died in provisioning, before the load window.

Per the stopping rule this consumes the one permitted re-run. A second void
closes the campaign as unresolved.

## Sitting 2: VOID (2026-09-05, substrate) — campaign CLOSED UNRESOLVED

The re-run cleared provisioning: Amendment 1's `POLYFORGE_EVAL_SHARED_PG=1` was
the right diagnosis, the tenants were created, and the sitting reached the load
window. It then ended `valid_runs: 0` at 477 s, rejected by the harness's own
validity guard:

```
replica sampler covered 7% of the load window (8 samples, 0 failed attempts):
infra cost would be under-counted
```

**The guard is right and the cause is upstream of it.** k6's log says why:

```
thresholds on metrics 'dropped_iterations, http_req_failed' were crossed;
at least one has abortOnFail enabled, stopping test prematurely
```

63 seconds into a 20 m 10 s window, with **10.6% of requests failing**. The
`crud_bursty` cell at `medium` asks for 1200–1443 VUs *per tenant* across eight
tenants; a four-node kind cluster on an eight-core laptop cannot serve that, so
k6 aborted and the sampler never got past eight samples.

**This is a substrate limit, not a controller result, and not a node result.**
Nothing here says anything about MN-H1: the load window never ran long enough
to measure spread, and `load_distribution.json` was never written. Scoring the
hypothesis from a 63-second fragment would be exactly the kind of salvage this
pre-registration exists to prevent.

**Per the stopping rule, two voids close the campaign as unresolved.** It is
closed. MN-H1, MN-H2 and MN-H3 are **not evaluated**, no `RESULTS_MULTINODE.md`
is written, and none of this is re-run under this pre-registration.

### What the campaign did establish, and what it leaves

Established, and it stands independently of the voids:

- **The instrumentation gap was real.** Node placement was never collected by
  anything in this repository; `LoadDistributionSampler` now resolves it. That
  finding came from reading the sampler, not from this campaign.
- **W7 was mis-diagnosed as GPU-blocked.** Both sittings ran the CRUD path with
  no GPU, no tier backend and no Kaggle, and both got further than the AI path
  ever has locally. The GPU was never the obstacle.
- **The obstacle is host capacity.** Eight cores cannot serve `crud_bursty` at
  `medium`. That is the same shape as B1's blocker — a substrate that cannot
  serve the cell's concurrency — arrived at from the opposite direction.

Left for a **new** pre-registration, if the question is worth another sitting:
a smaller cell (fewer tenants, or `crud_steady` rather than `crud_bursty`)
sized to what this host can actually serve, with the VU count justified against
measured capacity *before* the run rather than discovered by aborting one.
