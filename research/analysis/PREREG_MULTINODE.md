# Pre-registration: does the load actually spread across nodes? (W7)

Frozen and pushed before the campaign runs. The push event is the timestamp
anchor (cardinal rule R1).

## Question (and provenance)

`FINAL_ROADMAP` §0 lists W7 — *"Single machine, single cluster"* — among the
weaknesses a Transactions reviewer will raise, and recorded it as unclosable
without the GPU-blocked B1 matrix:

> Demonstrating multi-node *behaviour* needs a high-demand cell, i.e. the
> GPU-blocked B1 matrix. Partial credit is not available here and should not
> be claimed.

Session 43 checked that and found it wrong on both halves.

1. **The CRUD path needs no GPU.** The 24 h soak (`RESULTS_LIVE_SOAK_V8.md`)
   drove 298.6 rps across sixteen pods with no model in the loop. High demand
   was never what stood in the way.
2. **Node placement was never measured.** `LoadDistributionSampler` reads
   `kubectl top pods`, which carries a pod name and a CPU figure and nothing
   else. No live record in this repository says which *node* served anything,
   so no sitting — at any demand, on any number of nodes — could have produced
   node-level evidence. The sampler now resolves each pod's node and writes
   `node_of` / `node_shares` into `load_distribution.json`.

This campaign is the first use of that measurement.

## What this is NOT

- **Not multi-host, and not multi-zone.** Every node here is a container on
  one machine sharing one kernel, one disk and one NIC. This cannot speak to
  network partitions, zone failure, or cross-host latency, and a PASS must
  not be quoted as if it did. W7's residue after this campaign is "single
  *machine*", not "single node".
- **Not a performance claim.** Nothing here compares controllers or measures
  cost. The question is whether work lands on more than one node at all.
- **Not a replacement for B1.** B1 remains blocked on GPU concurrency and
  scores different hypotheses (WL-H1/H2/H3) on the AI path.

`jcac` alone: the question is about placement, not about which controller
places better, and a second arm would double the sitting for nothing this
prereg asks.

## Hypotheses (frozen)

**MN-H1 (the claim).** Work reaches more than one node: **at least 2 distinct
nodes appear in `node_shares`, and the busiest node's share is < 0.90.**

The 0.90 is deliberate and stated before any number exists. A perfectly even
4-node spread is 0.25 each; the scheduler is free to pack, and packing is not
the failure this asks about. The failure is *pinning* — attempt 4's port-forward
put effectively 100% on one pod, and that is the shape MN-H1 must be able to
catch. A busiest-node share at or above 0.90 is pinning by any reading.

**MN-H2 (gating, and it can fail).** The measurement is sound: **`node_of`
resolves a node for every pod that appears in `cpu_ms`** — i.e. `node_shares`
contains no `"unknown"` bucket — and the sampler took **≥ 10 samples**.

If MN-H2 fails, MN-H1 is **VOID rather than FAILED**: an unattributed pod
means the instrument did not work, and a claim about node spread built on a
partial attribution is exactly the vacuous-instrument failure this project has
already hit three times in WP14.

**MN-H3 (descriptive, no verdict).** Report the per-node shares and the pod
count. If the deployment ran at one replica the whole time, MN-H1 is
**VACUOUS** — one pod can only be on one node, and that is a statement about
the demand, not about the cluster. Recorded as such, not as a PASS.

## Outcome handling and stopping rule

- **One sitting.** If the cluster fails to come up or the harness marks the run
  invalid, the sitting is VOID, disclosed, and re-run at most **once**. Two
  voids close the campaign as unresolved.
- Verdicts are written to `RESULTS_MULTINODE.md` as measured. A FAIL is
  published with the same prominence as a PASS: "the load pinned to one node
  on a four-node cluster" would be a finding about the deployment, and a more
  interesting one than the PASS.
- The record is generated by `analysis_multinode.py` from the committed
  evidence, never written by hand, and registered in `scripts/reproduce.py`.

## What a PASS does and does not license

A PASS licenses exactly: *"the control plane's work was observed on more than
one node of a four-node cluster under CRUD load."* It removes "single node"
from W7's residue and leaves "single machine" standing, which is the honest
remainder and is already listed in §8 as permanent.

It does **not** license "distributed", "multi-host", "fault-tolerant", or any
statement about behaviour under node loss. Nothing here kills a node.
